# StationFlow · guion técnico para presentar en cinco minutos

**Borrador histórico: pendiente de actualizar a V9 antes de usarlo en vivo.** Ahora el empleado marca **Entered** con el ID, luego **Payment received**, después **Preparing** y **Ready**; el menú se llama **Hub burger**. La [guía operativa actual](DEMO_CELULAR_IPAD.md) y la [QA V9](QA_STATUS_V9.md) reflejan el código vigente.

Versión de ensayo local, 27 de septiembre de 2026. Jorge presenta y lee las frases en **negrita**; las indicaciones entre corchetes son acciones, no texto para decir. El objetivo es mostrar el recorrido completo en un celular y un iPad, con ambos en la **misma URL de la misma instancia del servidor**. El demo usa perfiles, menú, precios y pagos ficticios. No se ha probado todavía en esos dispositivos físicos ni se ha publicado en Cloudflare.

## Antes de subir al escenario

1. Iniciar el servidor local. En dos navegadores distintos de la Mac usar `npm run dev`; para celular/iPad en una red privada que permita conexión entre dispositivos, usar `npm run demo:lan` y la misma URL privada impresa en ambos. No usar `localhost` en el celular. La Mac y su proceso deben seguir encendidos. La guía detallada está en [DEMO_CELULAR_IPAD.md](DEMO_CELULAR_IPAD.md).
2. En el iPad, entrar como `manager` en `/staff/login` y elegir **Station controls → Demo service clock → Lunch**. Confirmar que The Hub está disponible, que **Campus burger**, **Seasoned fries** y sus opciones están activos, y que una franja tenga capacidad para **dos artículos**. Si se quiere mostrar una cola, usar **Simulate 3 orders** sólo si queda capacidad. Luego cerrar sesión y entrar como `hub` / `CampusDemo!26`, dejando abierto `/panel/hub`.
3. En el celular, abrir `/login`, listo para el ID ficticio `10001`. Mantener la página del ticket abierta y el teléfono despierto. El iPad y el celular necesitan sesiones distintas. Tener un código de recogida de respaldo anotado, pero usar el que genere el nuevo pedido en vivo.
4. Ensayar una vez con el reloj y la red elegidos. **No subir, desplegar ni abrir un túnel como parte de esta preparación.** La eventual URL pública requiere una decisión separada; el estado actual sigue siendo local.

## Preguntas probables

- **¿Por qué no usar Everyday?** Trevecca ya lo ofrece. Falta verificar si cubre estas estaciones y este proceso concreto; una integración o reutilización podría ser la mejor salida.
- **¿Se puede falsificar el ID?** Sí, los IDs `10001` y `10002` son públicos para el demo. Una versión real necesita autenticación institucional y autorización de pago.
- **¿Cómo evitan dos reservas del último cupo?** El servidor comprueba las unidades de todo el carrito y reserva dentro de una transacción SQLite. Los reintentos reutilizan una clave para devolver el ticket original.
- **¿El número en la cola mide la fila del comedor?** No. Cuenta tickets digitales activos con hora de recogida anterior o igual; no observa personas físicas.
- **¿Quién paga?** Nadie en este prototipo. Los precios y swipes son ejemplos; el personal confirma un pago ficticio. El POS, los saldos y los reembolsos no están integrados.
- **¿Y si el celular se bloquea?** El aviso visible se actualiza mientras el ticket está abierto y despierto. Las notificaciones push en segundo plano requieren otra implementación y pruebas.
- **¿Qué se probó?** Suite automatizada y build locales, más recorrido en navegador: burger y fries en un ticket, pago simulado, mensaje de pedido ingresado y aviso Ready. La comunicación en celular e iPad físicos y cualquier despliegue público siguen sin verificarse.
